# ファストフードポチ

マクドナルド・モスバーガー・松屋・松のや・吉野家・すき家・かつや・からやま・丸亀製麺の**期間限定・新登場メニュー**を1日1回巡回して記録し、
販売が終わって公式サイトから消えても記録が残るアーカイブにするサイト
（公開予定 https://fastfood.netaful.jp/ ）。栄養成分つき。KFCは公式サイトが
curlを拒否するため対象外。松屋・松のやは2026-10-11に追加。吉野家は5つ目、すき家は6つ目のチェーンとして追加（栄養成分・アレルゲンは公式PDFから読み取る。後述「公式PDFの読み取り」）。かつや・からやまは7つ目・8つ目（2026-10-11。公式サイトに栄養成分が無いので価格・発売日・販売状況のみ）。丸亀製麺は9つ目（2026-10-17。公式サイトの埋め込みJSONから栄養・アレルゲンまで取れる。後述）。

姉妹サイト [電書ポチ](https://book.netaful.jp/)・[家電ポチ](https://kaden.netaful.jp/)・
[林檎ポチ](https://apple.netaful.jp/)・[漫画ポチ](https://manga.netaful.jp/)・
[コンビニポチ](https://conbini.netaful.jp/)と同じく、基本はpip依存なし
(Python標準ライブラリのみ、HTML解析は正規表現)。構造は `conbini-pochi` のほぼ流用。
**例外が1つ**: 吉野家・すき家の栄養成分は公式PDFから読み取るため、`pdfminer.six`（純Python）だけを使う
（`requirements-pdf.txt` でバージョンを固定）。入っていなくてもクロールは動き、PDFの読み取りだけを飛ばす。
サイトの色は ティール `#00897B`、広告(AdSense、`adsense_client_id`/`adsense_ad_slot`)とGA4はconfigの値が空の間は何も出力しない。
広告はヘッダー下1枠＋カード一覧の中に12件おきに最大3枠(JSが並び替え・絞り込みのたびに差し込む。仕組みはコンビニポチと同じ)、商品ページは1枠。

## 使い方

```bash
python3 scripts/crawl.py                    # 全チェーンを巡回して data/products/ に蓄積
python3 scripts/crawl.py matsuya            # チェーンを指定すると、そのチェーンだけ巡回する
python3 scripts/fetch_netaful_reviews.py    # ネタフルのレビュー記事を取得・商品とひも付け
python3 scripts/generate_site.py            # docs/ 一式を生成
python3 -m unittest discover -s tests       # tests/fixtures/ の公式データのスナップショットでテスト
```

### PDF読み取りの準備（吉野家・すき家の栄養成分。手元の開発用）

```bash
python3 -m venv .venv                          # .venv/ は gitignore 済み
.venv/bin/pip install -r requirements-pdf.txt  # pdfminer.six==20251107（Python 3.9〜3.12で同じ結果）
.venv/bin/python scripts/crawl.py sukiya       # PDFを読むときは venv の python で実行する
```

venvを使わず素の `python3` で実行しても動く（pdfminer が無いので、PDFの読み取りだけを警告つきで飛ばす）。
CI（Actions）では `pip install -r requirements-pdf.txt` を先に実行する（失敗しても巡回は止めない）。
取得したPDFは `.cache/pdf/`（gitignore済み）に残り、HEADの指紋が同じ間は再取得しない。

定期実行は `.github/workflows/update.yml`（workflow_dispatchのみ。scheduleもpushトリガーも無い）を
Cloud Schedulerから起動する前提。**開発中は本番サイトを叩かず、tests/fixtures/ で開発する。**
`NTFY_TOPIC` は GitHub Secrets（コードに書かない）。

## 何を記録するか

- **限定メニュー**（期間限定・季節限定・地域限定・数量限定）と、**初回の巡回より後に初めて
  現れた新メニュー**。定番の既存メニューは詳細を取らない。初回に見えた全商品IDは
  `data/baseline_ids.json` に保存し、以後これに無いIDが出たら新メニューとして記録する。
- セット商品（名前に「セット」「コンビ」「募金付き」）は記録しない（バーガー本体と二重になり、
  栄養も載らないことが多いため）。
- 商品1件1ファイル `data/products/{mcdonalds|mos|matsuya|matsunoya|yoshinoya|sukiya|katsuya|karayama|marugame}/{id}.json`。既存ファイルは丸ごと上書きしない
  （初回取得が正。更新するのは last_seen_at / status / price_history 等の追跡項目だけ）。
- 画像は保存も表示もしない（`image: null`）。説明文は最初の1文（最大100文字）だけ保存し、
  引用ブロックで出典つきで表示する。価格・栄養成分・アレルゲン・販売期間・原産地は事実情報として全部出す。

### 販売状況の追跡（サイトの核）

- 巡回で一覧に居たら `last_seen_at`（日付）を更新し `status=on_sale`。
- **そのチェーンの一覧取得が全部成功した回だけ**、一覧から消えた商品を数える。
  一覧のどれか1ページでも取得失敗・0件（構造変更の疑い）・robots.txtでDisallowなら、その回は数えない。
- **別の日に連続2回**見つからなかったら `status=ended`、`ended_observed_at` にその日付。
  同じ日に何度実行しても1回と数える（`last_miss_date`）。
- 終了後に再登場したら `on_sale` に戻し、`relaunches` に記録。
- 一覧の価格が前回と違えば `price_history` に追記。
- 終了日は公式発表の最終販売日ではなく「公式の一覧から消えたことを確認した日」。サイト上にもそう書いている。

## 取得元

### マクドナルド (www.mcdonalds.co.jp)

- 巡回ページ（`config.json` の `mcdonalds_pages`）: `/menu/`（おすすめ）、`/menu/burger/`、`dessert/`、`side/`、
  `drink/`、`mccafe/`、`morning/`、`dinner/`。**`/menu/` のおすすめだけでは足りない**
  （月見バーガー単品や明治アーモンドチョコのフルーリー等は `/menu/` に出ない）。
  `/menu/set/` と `/menu/happyset/` はセット商品ばかりなので巡回しない。robots.txt は毎回取得し、
  Disallow のパス（`/mop/` `/order/` `/coupon-*` 等）には行かない。
- 限定判定: バッジ画像 `limit_badge.svg` に `data-time-limited-offer-started-at` が付いている、または
  バッジが `hidden` で隠されていない。**普通の商品もバッジのimg自体は持っていて `hidden` なので、
  `data-time-limited-offer='true'` の有無だけでは判定できない。**
- **商品ID** は一覧の `data-product-code`（`/products/{code}/` の code と一致する。deeplink の
  `code=NNNN` は別の値で画像パス用なので使わない）。
- 販売開始日: 一覧の `started-at` は告知用の日付で、実際の発売日より数日〜2週間早いことがある
  （月見バーガーは一覧8/18、実際の発売9/2）。詳細ページの `data-mop-availability-started-at`
  （モバイルオーダー受付開始）が実際の発売日と一致するのでこちらを `launch_date` に使い、一覧の値は `list_started_at` に残す。
- 終了予定: マクドナルドは公式の終了予定日を載せていない。詳細ページの
  `data-mop-availability-ended-at`（モバイルオーダー受付期間の終了）を「終了予定」として、
  その旨を明記して表示している（`mop_ended_at`）。公式の販売終了日と一致する保証は無い。
- 価格は税込（一覧ページに明記）。「460~」の「~」は最低価格、店舗・デリバリーで異なる場合がある。
- 栄養・アレルゲン・原産地は詳細ページのHTML。栄養が載らない商品（食べくらべポテナゲ等）は `nutrition: null`。
- 規約 `/policy/` は複製・転載・公衆への再提供を禁止している。→ 説明文は冒頭1文だけ・画像なし・
  出典つきの引用にとどめる運用（コグレ判断）。

### モスバーガー (www.mos.jp)

- `mos.jp` は `www.mos.jp` へ301でリダイレクトされる。最初から `www.mos.jp` を使うこと。
- 一覧はJSON `/data/menu/menu_category/{c_id}.json`。限定メニューは `c_id=26`。**新メニュー検出と
  終了判定のため全カテゴリ（`/data/menu/mst_navi.json` の12個）を毎回取る**（1日13リクエスト）。
  限定アイコン（`/data/menu/mst_icon.json`: 1=期間限定, 2=季節限定, 4=地域限定, 5=店舗限定, 14=数量限定）が
  付いた商品は他カテゴリのものも限定として記録する（朝モスの店舗限定トースト等）。
- **アレルゲンの対応表がある**: `/data/menu/mst_allergy.json`（`/menu/allergy/` のJS `allergy.js` が読んでいる）。
  `level=5`（●）が「含む」、`1`（－）が含まない、`2,3,4,6`（△▽◇等）は凡例が必要な条件つきの表示で、
  サイトでは記号つきで「条件つきの表示」として出す。
- 発売日・終了予定は `explain` の「【2026年9月9日（水）〜2026年11月上旬頃までの販売予定】」から正規表現で取る
  （無ければ null。時間限定・曜日限定のメニューには無い）。
- 詳細ページのHTMLは取らない（JSONに全部入っている）。公式URLは
  `https://www.mos.jp/menu/detail/?menu_id={id}&c_id={c_id}`。
- 規約ページは見つけられていない（`/terms/` `/sitepolicy/` は404、トップのフッターはJS描画）。
  robots.txtは無い（404）。サイトのフッターに公式サイトへのリンクを置く程度にしている。

### 松屋 (www.matsuyafoods.co.jp/matsuya/)

- 松屋には「NEW」「期間限定」の公式ラベルも販売期間も無い。記録の対象は
  (a) 「おすすめ」一覧（`/matsuya/menu/limited/`）に載った商品、
  (b) baseline（初回巡回時の全メニューID）に無く、後から現れた商品。
  `limited_kind` は、ニュースに発売のお知らせがあれば「新メニュー」、無ければ「おすすめ掲載」
  （おすすめに載らず新規に現れただけなら「新規掲載」）。「期間限定」とは書かない。
- 一覧は静的HTML。入口 `/matsuya/menu/` から12カテゴリ（おすすめ・牛めし・カレー・丼・定食・モーニング・
  牛めしランチ・カレーランチ・おこさま・サイドメニュー・セットメニュー(topping)・ドリンク）を毎回取る（1日14リクエスト）。
  **終了判定は「おすすめ」ではなく全カテゴリの一覧からの消失**（全カテゴリ取得成功の回だけ・別の日に連続2回）。
  セットメニュー(topping)だけに現れた商品と「＜選べるサイド＞」等の選択肢は記録しない（baselineには入る）。
- 商品ID は詳細URLのパス（`/matsuya/menu/` 以降）を `-` でつないだもの（例 `curry-kashmir_hp_261006`）。
  詳細リンクは `/menu/../` を含むので正規化している。slug末尾の6桁は掲載日（YYMMDD）で、同じ商品でも更新で
  slugが変わりうる。同じ名前の商品が別slugで現れたら別レコードとして記録し、`same_name_as` に旧IDを残す。
- 詳細ページ（静的HTML）: 価格（税込）は「ラベル無し（セット等）＋単品」または「小盛／並盛／大盛」の複数。
  代表の価格は ラベル無し→並盛→先頭 の順（一覧の価格と一致する）。`price_variants` に全部残す。
  栄養成分も同様に複数あり、代表を `nutrition`、複数のときは全部を `nutrition_variants`（`[{label, nutrition}]`）に保存する。
  基準日（「2026年10月6日現在」）は `nutrition_as_of`、「みそ汁・福神漬も含まれる」等の注記は `nutrition_note`。
  アレルゲンは「○」が含む、「△」（原材料の生産工場で当該原材料を含む製品を製造）はモスと同じ条件つき表示（`partial`）。
- **説明文と発売日は商品ページに無く、ニュースにある。** `/matsuya/whatsnew/data/whatsnew.json`（約65万バイト）の
  category=menu の記事のうち、見出しに商品名（正規化して部分一致）を含むものを探し、記事ページの「【発売日】」を
  `launch_date`、冒頭の見出し文（h4）の1文を説明文にする。新規商品があるときだけJSONと記事を取り、同じ記事は1回しか取らない。
  見出しの照合は商品のslug日付の前120日〜後14日のニュースだけを対象にする（「新牛めし」のような短い名前が
  何年も前の別商品の見出しに含まれる誤爆を避ける）。
  1本の記事が複数商品をまとめて紹介する（「ネオカシミール」6品）ため、見出しに無い商品は掲載日付近の記事の
  本文に商品名があるかを調べる（1回の実行で最大4記事）。見つからなければ `launch_date: null`（`launch_date_source` に由来）。
- 終了日は公式に書かれない。「一覧から消えたことを確認した日」とサイトにも明記。画像は保存も表示もしない。
- robots.txt は全許可（`Allow: /`）、ボット対策なし。規約 `matsuyafoods-holdings.co.jp/sitepolicy/` は私的利用を超える
  複製・転載と営利目的の行為を禁じている（自動取得への言及なし）。→ 広告は2026-10-16にコグレ判断で導入（規約リスクは説明済み）。説明文は冒頭1文だけ・出典つき引用。

### 松のや (www.matsuyafoods.co.jp/matsunoya/)

松屋とサイト構造が同じ（松屋フーズ系）なので、パーサ・巡回・ニュース照合は松屋と共通のコードで、
チェーンのslug（= URLの接頭辞 `/{slug}/menu/` ・ `/{slug}/whatsnew/…`）で切り替える
（`parsers.MATSUYA_FAMILY`、`crawl.crawl_matsuya_family`）。違うのは次の点だけ（2026-10-11に実物で確認）。
- 「おすすめ」カテゴリのslugは `osusume`（松屋は `limited`）。8カテゴリ（osusume・teishoku・moriawase・donburi・
  okosama・morning・souzai・side_menu。入口 `/matsunoya/menu/` から毎回拾う、1日10リクエスト）。
  「記録しないカテゴリ」は無し（松屋のtoppingに当たるものが無い）。カテゴリの表示名は `config.json` の `matsunoya_categories`。
- 商品ID は `/matsunoya/menu/` 以降を `-` でつないだもの（例 `teishoku-tei_kaki5_hp_260916`）。保存先のディレクトリ
  （`data/products/matsunoya/`）とbaseline（`data/baseline_ids.json` の `matsunoya`）がチェーンごとに別。
- ニュース見出しで省かれる接頭辞は「松のやの」。ニュースJSONは `/matsunoya/whatsnew/data/whatsnew.json`（約38万バイト）。
- 初回の記録は「おすすめ」23件。見出しに商品名が無い商品が多く（惣菜セット・盛合せ等）、発売日の照合は9/23件
  （本文探索は1回の実行で最大4記事）。照合できない商品は `launch_date: null`。
- 規約・robots.txt・引用の方針（説明文は冒頭1文・画像なし）は松屋と同じ松屋フーズHDのサイトポリシー。
- 巡回時間: 全9チェーンの1回の実行上限は 60+30+60+60+60+80+10+10+30=400リクエスト、3秒間隔でも約20分（待ち時間のみ。かつや・からやまは通常日それぞれ3リクエスト、丸亀製麺は通常日6リクエスト）で、workflowのtimeout（60分）に収まる。


### 吉野家 (www.yoshinoya.com) — 第1段階

静的HTML。栄養成分・アレルゲンは別PDF（`/pdf/allergy/`「吉野家メニュー情報」、原産地は `/pdf/producing_area/`）で、
**栄養成分・アレルゲンはこのPDFから読み取る**（後述「公式PDFの読み取り」。URLは `config.json` の `yoshinoya_pdf`）。
PDFに名前が完全一致しなかった商品は、公式PDFへのリンクで案内する（`nutrition` は null）。
お知らせの見出しのリンクもPDFだが、取得せず見出しの文言だけを読む。
- 規約 `/sitepolicy/` は営利・非営利を問わず複製・転用と営利目的の行為を禁じている（自動取得への言及なし）。
  robots.txt はステータス404だが本文は全許可のYoast形式（`User-agent: * / Disallow:` 空）→ 404のときは全許可として扱い、
  本文が取れればそのDisallowに従う。→ **記録するのは事実情報（価格・日付・販売状況）だけ。説明文・画像は保存も表示もしない。**
- 入口 `/menu/` の12カテゴリ（期間限定 `gentei`・牛丼・牛丼麺セット・丼・から揚げ・定食・おかず・カレー・鰻・朝食・お子様・サイドメニュー/飲み物）を
  毎回リンクからたどって取る（1日14リクエスト＝robots＋入口＋12。記録対象外のカテゴリは無し。料理でない案内（「温め直し方」等、価格なし）だけ除外）。
  リンクは末尾スラッシュ無しの絶対URLで書かれているので正規化して解決する。
- 記録するのは (a) 「期間限定」一覧に載った商品、(b) baseline（初回巡回の全メニュー99件）に無く後から現れた商品。定番の既存メニューは詳細を取らない。
  `limited_kind` は一覧のバッジに従い「期間限定」/「新メニュー」（NEWのみ）/「新規掲載」（どちらも無い）。
- **商品ID** は詳細URLの `カテゴリ-slug`（例 `yoshinoyanodon-tsukimi_gyutoji_don`）。同じ商品が複数カテゴリの一覧に載ってもURLは同じ。
- **slugの使い回し（季節商品の再登場）**: 終了（別の日に連続2回、全カテゴリ一覧の取得が全部成功した回だけ）の後、同じIDが一覧に戻ったら
  `relaunches` に記録して `on_sale` に戻し、昨季の発売日・終了日・お知らせ見出しは `seasons` に残す。今季の `launch_date` は一度 null に戻して
  お知らせの見出しから探し直す（昨季の日付を今季として出さない）。再登場時の価格を `price_history`（`relaunch: true`）に足す。
- 詳細ページ（新規に見つけたとき1回だけ取得）: 店内の税込価格（サイズ別）と、税込額が違うテイクアウト価格（`price_variants`、
  「並盛・テイクアウト」のようなラベル）、テイクアウト可否（`takeout`）。代表の価格は「並盛」→先頭（一覧の価格と一致）。
- **発売日・終了告知はお知らせ一覧 `/news/{年}/` の見出し**から取る。見出しの「10月8日より…販売」「本日より販売開始」を発売日にし、
  年はお知らせの日付から補う。商品名は見出しの「」『』の中身と**完全一致**のときだけ採用（「さんま定食」が「牛さんま定食」の見出しに
  部分一致する誤爆を避ける）。括弧の無い見出しだけ4文字以上の部分一致。公式通販のお知らせ・TVCMの放映開始は除外。
  商品の初観測日（再登場は再登場日）の前120日〜後14日のお知らせだけを対象にする。照合できなければ `launch_date: null`
  （`launch_date_source: not_found`）。発売日が未確定の商品は、取得済みのお知らせで毎回探し直す（追加のリクエストなし。1〜4月は前年分を1回取る）。
  見出しに商品名つきの「（早期）販売終了のお知らせ」があれば `early_end_notice` に付記する（status は一覧からの消失で決める）。

## 公式PDFの読み取り（吉野家・すき家の栄養成分・アレルゲン）

`scripts/pdf_nutrition.py`（pdfminer.six で文字と座標を取り、表を組み立てる純粋関数）と
`scripts/pdf_update.py`（取得・更新検知・検証ゲート・商品への反映）。巡回（`crawl.py`）のあとに1回走る。

- **表の読み取り**: PDFの表はメニュー名のセルが複数サイズの行をまたぎ（セル結合）、縦に1文字ずつ分割された名前もある。
  素のテキスト順では名前と数値が対応しないので座標を使う。すき家(栄養)=セル罫線で名前セルの上下端を取り、その中の数値行を割り当てる／
  複数メニューを1セルに並べたブロックは、名前をサイズ行の中央の高さで割り当てる（合わなければ採用しない）。
  すき家(アレルゲン)=見出し番号1〜28の列位置と記号 ●△- のxを対応づける。吉野家=縦罫線で列・名前セルの横罫線で行のまとまりを取り、
  ○▲は文字単位のxで品目の列に対応づける（食塩の数値に最初の記号がくっつくセルがあるため）。
  吉野家は英語・中国語・韓国語のページが同じ品目で重複するので、見出し「栄 養 成 分」と単位「(kcal)」がある日本語ページだけを使う（ページ番号は決め打ちしない）。
- **照合**: 商品名とPDFのメニュー名をNFKC正規化・空白除去（波ダッシュ〜も同一視）したうえで**完全一致だけ**。曖昧な部分一致はしない。
  同名で値が違うブロックが複数あれば採用しない。一致しない商品は従来どおりPDFへのリンク。
- **商品データ**: `nutrition`（代表=「並盛」があれば並盛、なければ先頭行）、`nutrition_variants`（代表が先頭のサイズ別。2件以上のとき）、
  `nutrition_source`（PDFのURL・版・取得日時）、`nutrition_note`、`allergens`（`contains`＝●○／`partial`＝△▲）、
  `allergens_conditional`（記号とPDFの凡例の意味）、すき家はアレルゲンの出典 `allergen_source`、`pdf_tried`（試した版）。他のフィールドは変えない。
  吉野家でサイズごとにアレルゲン記号が違うときは、安全側（どれかのサイズで含むなら含む）。
- **検証ゲート**: (1)エネルギー検算（kcal ≈ 4×たんぱく質+9×脂質+4×炭水化物、±15%または±6kcal）に外れる行は採用しない
  (2)見出しが見つからない／読み取れた行が80行未満／検算の通過率80%未満／更新日・号数が無い、または照合した商品の半分以上が検算で落ちる、
  のいずれかなら**その回は何も更新せず**、`data/pending.json` の `pdf:*` と標準エラーに理由を残して続行
  (3)同じ版（すき家=更新日、吉野家=号数＋日付）の間は、一度入れた値を上書きしない。
- **更新検知**: PDFは毎回取らない。HEADの指紋（ETag・Last-Modified・Content-Length）が `data/pdf_state.json` の記録と違うときだけ取得して解析する。
  栄養が空で、まだこの版で試していない商品があるときも1回だけ取得して試す（`pdf_tried`）。読み取れなかったファイルと同じ指紋は取り直さない。
  **吉野家のPDFはHEADに指紋が無い**（動的配信）ので、前回の取得から7日たったら取り直して号数で確かめる。
  1回の実行で取得（GET）するPDFは、すき家2本・吉野家1本まで（HEADは各1回別に）。キャッシュ `.cache/pdf/` の指紋が同じならGETもしない。
- **規約**: 両社とも複製・転載を禁じているため、PDFの表を丸ごと保存・公開しない。記録している商品に一致した行の数値（事実情報）だけを商品データに入れ、
  画像・説明文は載せない。`images.zensho.co.jp` の robots.txt は403を返す（PDF本体は200）。公式のメニューページが直接リンクしているURLを、更新があったときだけ取得する。
  403/429/チャレンジなら回避せず、その回のPDF取得を止める。
- **テスト**: 公式PDFの実データは使わず、構造を再現して名前・数値を創作した合成フィクスチャ（`tests/pdf_fixtures.py`）で行う。
  `.cache/` に実PDFがあるときだけ走る結合テストが `tests/test_pdf_site.py` にある（CIでは走らない）。

## クロールのマナー

- User-Agent は正直なもの `FastfoodPochi/1.0 (+https://fastfood.netaful.jp/)`。ブロック（403/429・チャレンジ）されたら
  **ブラウザ偽装に切り替えず**、そのチェーンの処理を止めて `stats.blocked` に記録する（他チェーンは続行）。
- リクエスト間隔は3秒以上、タイムアウト20秒、リトライは1回。1回の実行のリクエスト上限は
  `max_requests_per_run`（マクドナルド60・モス30）。通常の1日は、マクドナルド9（robots.txt＋一覧8）＋新メニューの詳細、
  モス13（カテゴリ一覧＋12）＋（新メニューがあれば）アレルゲン表1。
- 取得済みの商品の詳細ページは再取得しない。取得失敗はチェーン単位で `data/pending.json` に記録し、次回再試行する。
- `data/run_summary.json`（今回の新規・終了の件数。gitには入れない）を notify.py が読む。
  日付で数えるとUTC/JSTのずれで誤通知になる（コンビニポチで実際に起きた）。

## サイトの構成（docs/）

- トップ: 販売中の限定メニューをチェーンごとにグルーピング（開始日の新しい順）。並び替え（開始日順/カロリー順）、
  販売状況の絞り込み（販売中/終了/すべて）、チェーンの絞り込み、メニュー名検索（`search-index.json`）、
  ネタフルの最新レビュー。最近30日以内に終わったメニューも載せておき、既定の「販売中」では隠れる。
  トップに WebSite 構造化データ（name=ファストフードポチ。無いと検索結果のサイト名が親ドメインの「ネタフル」になる）。
- `/archive/` と `/archive/YYYY-MM/`: 終了した限定メニューを**開始月ごと**に。各カードに「いつからいつまで」。
- `/chains/{mcdonalds|mos}/`、`/items/{chain}-{id}.html`（販売期間・価格と価格履歴・栄養成分・アレルゲン・原産地・出典つき引用）。
- ページの title/description にチェーン名・カロリー・価格（例「マクドナルド「○○」のカロリー・価格・栄養成分｜ファストフードポチ」。
  栄養が無い商品は「価格・販売期間」）。favicon.png は96px（48の倍数が必要）。
- RSS（新しく記録した商品）、sitemap.xml、robots.txt（AI学習専用クローラーを拒否）、OGP、CNAME、.nojekyll。
  生成時に古い `items/` と `archive/` のページを掃除する。商品が0件のページに空の見出しは出さない。

## ネタフルのレビュー連携

`fetch_netaful_reviews.py` が WordPress REST API（認証不要）から記事を取り、商品名と「」内の名前を照合する
（コンビニポチと同じ厳しさ: 6文字以上の部分一致、記事が発売日の14日超前なら除外）。
タグID: マクドナルド=735（208件）、モスバーガー=882（**3件しか付いていない**）、松屋=729（254件）、松のや=937（70件）、吉野家=765（56件）。
松屋のタグには松のやの記事が4件混ざる（タイトルに「松のや」を含む）。タイトルに「松のや」を含む記事は松のや側だけに出し
（`【松屋・松のや】` も松のや側）、松屋側からは外す（`config.json` の `netaful_title_excludes` / `netaful_title_always`、
キャッシュ済みの記事にも判定をかける）。松のやのタグには「松乃家」など無関係の記事も付くので、タイトルに「松のや」を含むものだけ採用する。
吉野家のタグにもタイトルに「吉野家」を含まない記事が混ざりうるため、タイトルに「吉野家」を含むものだけ採用する。すき家=869（78件）、かつや=874、からやま=877 も同様に、タイトルに「すき家」を含むものだけ採用する。丸亀製麺=890（4件）は後述の記事検索も併用する。
モスはタグ付けが少ないため、記事検索（search=モスバーガー）の結果のうちタイトルに「モスバーガー」「モス」を含むものも採用している。
関連記事のキーワード辞書は `config.json` の `related_keywords`（商品名とネタフル記事タイトルの実データで選んだ）。

## テストのフィクスチャ（公式ページのコピーはリポジトリに入れない）

`tests/fixtures/` には、各社の公式サイトから取得したページ・データのスナップショット（マクドナルド・
モスバーガー・松屋・松のや・吉野家・すき家・かつや・からやま・丸亀製麺）を置いて、パーサのテストに使う。**各社の規約が複製・転載を
禁じているため、これらはリポジトリに入れていない**（`.gitignore` で除外。2026-10-11に追跡から外した。
それ以前のコミットには残っている）。ファイルの一覧は `tests/fixtures_manifest.txt`。

- 手元にフィクスチャが無い環境（新しく clone した場合など）では、それを使うテストは**自動でスキップ**される
  （`tests/helpers.py` の `fx()`）。PDF読み取りのテストは、名前と数値を創作した合成データ
  （`tests/pdf_fixtures.py`）で行うので、フィクスチャが無くても動く。
- 手元でフィクスチャを使ったテストを動かすときは、一覧のファイル名で公式のページを自分で取得して置く。
  取得は、間隔3秒以上・必要最小限にする。
